**Result: TP4 (tensor parallel over four cards) decodes one stream at 129.1 tok/s, 50% faster than TP2 at 86.0 tok/s.** At 16 concurrent requests TP4 reaches 969.0 tok/s aggregate. Two independent TP2 instances running side by side reach 772.2 + 664.0 tok/s at 16 + 16 requests. The workload is synthetic and favours speculative decoding, so these numbers are **not comparable** with the dual-host headline of 78 to 84 tok/s in the [model card](../README.md).

All runs happened while the CPU-to-switch uplink was trained at PCIe Gen1 x16. Host-to-GPU copies ran at 3.6 GB/s, but GPU-to-GPU copies stay inside the switch and ran at 28.5 GB/s per pair. The uplink was retrained to Gen4 on 2026-09-24, after these runs. See [findings/pcie-switch-uplink-can-train-at-gen1.md](../../../findings/pcie-switch-uplink-can-train-at-gen1.md). Decode traffic between cards does not cross the uplink, so the Gen1 link should mostly have slowed model loading, not decode. That is an inference, not measured.

## Workload

| | |
|---|---|
| Workload set | not a standard set: one fixed prompt, below |
| Input length | one short English prompt (under 40 tokens, not measured) |
| Output length | 512 tokens, `ignore_eos` |
| Sampling | greedy (temperature 0) |
| Warm-up | 1 request discarded |
| Repetitions | 1 pass per concurrency level (1, 4, 16) |

Every request is the same prompt, so all streams generate the same text. This favours MTP and is the main reason not to compare with other workloads. Per-stream tok/s is the mean over requests of output tokens divided by that request's wall time, so it includes time to first token (small for a short prompt). Aggregate tok/s is all output tokens divided by the wall time of the whole batch.

Command (`bench.py`, our own script, run on the host against each instance):

```python
import json, sys, threading, time, urllib.request

BASE = sys.argv[1] if len(sys.argv) > 1 else "http://127.0.0.1:18082"
MAX_TOK = 512
PROMPT = ("Write a detailed technical explanation of how a PCIe switch routes peer-to-peer "
          "transactions between two endpoints, covering address routing, ACS, and credits.")

model = json.load(urllib.request.urlopen(BASE + "/v1/models"))["data"][0]["id"]


def one(results):
    body = json.dumps({"model": model, "prompt": PROMPT, "max_tokens": MAX_TOK,
                       "temperature": 0.0, "ignore_eos": True}).encode()
    req = urllib.request.Request(BASE + "/v1/completions", data=body,
                                 headers={"Content-Type": "application/json"})
    t = time.perf_counter()
    r = json.load(urllib.request.urlopen(req, timeout=600))
    results.append((r["usage"]["completion_tokens"], time.perf_counter() - t))


print(f"model={model}", flush=True)
one([])  # warmup
for conc in (1, 4, 16):
    res = []
    ths = [threading.Thread(target=one, args=(res,)) for _ in range(conc)]
    t = time.perf_counter()
    [x.start() for x in ths]
    [x.join() for x in ths]
    wall = time.perf_counter() - t
    toks = sum(n for n, _ in res)
    per = sum(n / s for n, s in res) / len(res)
    print(f"concurrency {conc:2d}: per-stream {per:6.1f} tok/s | aggregate {toks / wall:7.1f} tok/s", flush=True)
```

## Observations

- **Driver-held host RAM stayed bounded with the sleep-mode allocator.** "Driver-held" is the watchdog's unaccounted memory: `MemTotal - MemFree - Buffers - Cached - SwapCached - AnonPages - Slab - KernelStack - PageTables - VmallocUsed`. It was 2.1 GiB before each run. Earlier TP4 attempts without the sleep-mode allocator reached 92 to 104 GiB and took the host down; see the experiment and [findings/xe-vram-overcommit-spills-into-host-ram.md](../../../findings/xe-vram-overcommit-spills-into-host-ram.md).

  | Run | Peak driver-held | While benchmarking | Lowest MemAvailable (121 GiB usable) |
  |---|---|---|---|
  | TP4 | 20.8 GiB (during start-up) | 11.8 to 12.6 GiB | 86.4 GiB |
  | TP2 alone | 12.3 GiB | 6.9 to 7.7 GiB | 100.1 GiB |
  | 2x TP2 | 20.7 GiB (both lanes loading at once) | 11.5 to 12.5 GiB | 83.5 GiB |

  Source: [raw/2026-09-23-tp4-quad-b70-host-ram.csv](raw/2026-09-23-tp4-quad-b70-host-ram.csv). Swap use stayed at 0.1 GiB.
- **VRAM ran within about 1 GiB of full.** During the TP4 benchmark `xpu-smi` reported 31,244 to 31,642 MiB used per card. vLLM allocated 18.7 GiB of KV cache per card, while its own log said 17.13 GiB would fully use the card and 15.79 GiB would fit `--gpu-memory-utilization 0.90`. vLLM on XPU does not count graph memory when sizing the KV cache ([vLLM v0.28.0 gpu_worker.py](https://github.com/vllm-project/vllm/blob/v0.28.0/vllm/v1/worker/gpu_worker.py)), and overflow spills silently into host RAM, so set `--kv-cache-memory-bytes` below the "fully utilize" value.
- **Start-up time.** TP4 engine init took 136.3 s, of which 102.2 s was compilation (cold compile cache). TP2 took 125.1 s (95.8 s compiling). Model loading took 4.71 GiB per card at TP4 and 9.26 GiB at TP2. These and the KV figures above come from the vLLM server logs.
- **All four workers opened every GPU.** `ZE_AFFINITY_MASK` was unset for TP4, and the per-worker affinity patch does not take effect in vLLM 0.28.0 when `--device-ids` is not passed: `_resolve_device_ids()` returns None ([vLLM v0.28.0 engine/utils.py](https://github.com/vllm-project/vllm/blob/v0.28.0/vllm/v1/engine/utils.py)). The xe fdinfo of each worker showed DRM clients on all four cards.
- **Correctness was not checked.** No greedy comparison against a non-speculative reference was run, at any concurrency. vLLM 0.28.0 labels multi-GPU XPU graphs experimental ([vLLM v0.28.0 platforms/xpu.py](https://github.com/vllm-project/vllm/blob/v0.28.0/vllm/platforms/xpu.py)). Treat these numbers as speed only.
- Power draw, temperatures and clocks were not logged.
