## Result

A cold 135K read took 286.44 s with `-b 3072` against 283.66 s with `-b 2048`: no gain. Reverted the same day. The decode and acceptance figures of this session are not usable, because the model repeated the same answer from turn 2 on.

## Hypothesis

With `-b 2048 -ub 1536`, llama.cpp splits every 2,048-token batch into one micro-batch (ubatch) of 1,536 tokens and one of 512. A 134,862-token read therefore runs 132 ubatches, 66 of each size. Each ubatch pays fixed costs: the host-side input setup (about 32-37 ms per ubatch for the target model in the `LLAMA_HOST_PROF` timing; source: server journal excerpt, not archived), the graph build, one draft-model pass, and the per-op launch overhead. The 512-token ubatch also runs every grouped MoE (mixture-of-experts) GEMM (general matrix multiply) with a third of the rows over the same set of experts, so it reads the expert weights at a third of the arithmetic intensity. `-b 3072` splits every batch into two full 1,536-token ubatches: 88 ubatches instead of 132. Expected: a few percent off a cold read (estimate). No change to decode or to prompt turns, which are far below one ubatch.

The 1536/512 alternation is visible in [raw/2026-09-26-fa-selection-union.csv](../benchmarks/raw/2026-09-26-fa-selection-union.csv): the `n_q` column of the logged attention calls alternates 1536 and 512 through a cold read on the default flags.

## Change

```diff
- -b 2048 -ub 1536
+ -b 3072 -ub 1536
```

Runtime drop-in on the production service; build unchanged (`20260926-2b84213a4`).

## Procedure

[`tools/lcbench.py`](../../../tools/lcbench.py) with `LC_TOKENS=135000 LC_TURNS=6 LC_PREDICT=256`: one cold read of the fixed 134,862-token C++ context, then 6 greedy turns of 256 tokens. The baseline session on the same build with the default flags ran 10 turns earlier the same night. Cold reads are also logged server-side as progress lines every 30,720 tokens; those rows are in the progress CSV.

### Why the decode figures of this session are invalid

The `lc-test.json` summary reads: decode median 62.4 tok/s (47.1-62.6), acceptance 93.1% (1125/1209), 64.4 ms per step, prompt median 1.53 s ([summary CSV](../benchmarks/raw/2026-09-26-lcbench-sessions-summary.csv)). These are not comparable with any other session in this repository. From turn 2 on the model produced the same answer in every turn (source: session log, not archived; generated text is not stored). A repeated answer is trivially predictable for the MTP draft, which inflates acceptance and therefore tok/s. The per-turn rows show it: from turn 2 on the draft was accepted 96.4-100% of the time (190/195, 189/196, then 191/192, 191/191 and 191/191 in turns 4-6), against 50-89% per turn in every other session ([per-turn CSV](../benchmarks/raw/2026-09-26-lcbench-sessions-per-turn.csv)).

| Turn | New prompt tokens | Prompt time | Draft accepted / drafted | Acceptance | Decode tok/s |
|---|---|---|---|---|---|
| 1 | 61 | 0.80 s | 173 / 244 | 70.9% | 47.1 |
| 2 | 60 | 0.64 s | 190 / 195 | 97.4% | 62.0 |
| 3 | 375 | 1.81 s | 189 / 196 | 96.4% | 60.7 |
| 4 | 321 | 1.53 s | 191 / 192 | 99.5% | 62.5 |
| 5 | 58 | 0.58 s | 191 / 191 | 100% | 62.4 |
| 6 | 416 | 1.81 s | 191 / 191 | 100% | 62.6 |

Whether `-b 3072` caused the repetition is unknown; the batch size does not touch decode, and the same build decoded normally with `-b 2048` (10 turns, 63.8% acceptance). The prompt median (1.53 s) is not comparable with the default session's 0.76 s either: it is the median of three short (58-61-token) and three long (321-416-token) turns, and no per-turn data of the 10-turn default session is archived. The long turns took 1.53-1.81 s here, against 2.6-3.0 s for ~400-token turns on the 2026-09-25 builds ([agent-session benchmark](../benchmarks/2026-09-25-agent-session-135k.md)).

## Correctness

Not assessed beyond the observation above. The change was reverted on speed alone, and its decode output was degenerate for reasons not attributed to the flag.

## Decision

Reverted. Production keeps `-b 2048 -ub 1536`. The per-ubatch fixed costs that `-b 3072` removes are not where the remaining cold-read time goes; see the [prefill op profile](../benchmarks/2026-09-26-prefill-op-profile.md) for where it does.

## Follow-ups

- [ ] If a repeated-answer session shows up again, check whether it reproduces with the default flags before attributing it to a change. A repetition check (identical turn outputs) belongs in `lcbench.py`'s summary line.
