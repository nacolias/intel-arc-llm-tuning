# quad-b70-5800x-pex88096

Four Arc Pro B70 cards behind one Broadcom PEX88096 PCIe switch, on a Ryzen 7 5800X desktop board. This is the [dual-b70-5800x](dual-b70-5800x.md) box after its upgrade to four cards on 2026-09-23.

Headline results on this host: Qwen3.8-27B at vLLM TP=4, 129.1 tok/s single-stream ([benchmark](../../models/qwen3.8-27b/benchmarks/2026-09-23-tp4-quad-b70.md)), and Qwen3.8-Flash-Next on llama.cpp SYCL across all four cards ([model folder](../../models/qwen3.8-flash-next/)).

### Topology

```
CPU root port (PCIE1, x16) ── SlimSAS host adapter + cables ── 16 GT/s x16 uplink
└── Broadcom PEX88096 (one chip, 1000:c010, synthetic hierarchy)
    ├── 16 GT/s x16 ── GPU0  ASRock B70
    ├── 16 GT/s x16 ── GPU1  ASRock B70
    ├── 16 GT/s x16 ── GPU2  Intel reference B70 (boot VGA, drives a local console)
    ├── 16 GT/s x16 ── GPU3  ASRock B70
    ├── one empty x16 port, two x1 ports
    └── management endpoint (class 0x0180, no driver bound)
```

- **One chip, synthetic hierarchy.** Every switch function reports the same device serial number, so it is one PEX88096. Its firmware presents a nested virtual bus tree in which GPU2 and GPU3 share a branch. That sharing is only logical: two disjoint pairs copying at once through that branch reached 56.9 GB/s. Matching the virtual ports to Broadcom's "synthetic" mode is an inference from the port layout and the [PEX88000 brief](https://docs.broadcom.com/doc/BC-0484EN).
- **The subsystem ID is Broadcom's default** (1000:a096), so the board maker cannot be read from software.
- **Each B70 has its own internal switch.** Upstream port 8086:e2ff (the physical slot link), downstream bridges 8086:e2f0 and 8086:e2f1, the GPU 8086:e223 under e2f0, and an audio function 8086:e2f7 under e2f1. The GPU endpoint's own link reads 2.5 GT/s x1; that is the fixed internal link, not a fault.
- **Max payload size is 256 B on every hop.** The larger values in `lspci` are capabilities, not settings. GPU max read request is 512 B.
- **ACS (Access Control Services) is off** on the switch downstream ports, so peer-to-peer (P2P) traffic turns around inside the switch.
- The switch ports advertise a 25 W slot power limit; the cards draw from their own power connectors.

## Notes

- **The switch uplink trained at Gen1 once.** On the boot after a kernel panic (2026-09-23) the CPU-to-switch link came up at 2.5 GT/s x16, and host bandwidth fell to 3.6 GB/s for all four cards. A runtime retrain failed. A cold start with the SlimSAS cables reseated fixed it on 2026-09-24. Check `current_link_speed` of the root port after every boot. See [finding](../../findings/pcie-switch-uplink-can-train-at-gen1.md).
- **VRAM overcommit spills into host RAM.** Over-allocating a card does not fail: the overflow goes into unswappable host RAM held by `xe`. vLLM TP=4 without the sleep-mode allocator reached 92–104 GiB of driver-held RAM and crashed the box once. Watch `MemTotal − MemAvailable − AnonPages` and run a watchdog on every multi-GPU load. See [finding](../../findings/xe-vram-overcommit-spills-into-host-ram.md).
- **The switch board has its own PSU.** Whether it switches off with the host is unknown. A firmware update or a link problem needs a full power cycle that includes it.
- **Test-window practice.** Before any test, stop every GPU service and the timers or guards that restart them. Keep one GPU tenant per card. Run a host-RAM watchdog with a MemAvailable floor during loads. Do not measure idle power while anything polls the cards.
- **Debugfs hazards for audit scripts.** Reading `/sys/kernel/debug/ttm/tt_shrink` triggers a TTM swapout, and reading `xe` `gt*/force_reset*` resets the GT. Safe to read: `gtt_mm`, `tile0/vram_mm`, `gt*/uc/*_info`, `ttm/page_pool`, `dgfx_pkg_residencies`, `dgfx_pcie_link_residencies`.
- **No D3cold.** The root port has no ACPI `_PR3` power resource, and nothing on the switch path supports hotplug, so idle cards cannot be powered off.
- **GPU2 drives a console.** With the console lit it never runtime-suspends and idles at 11 W with ASPM L1; blanked, 5 W.
- **No AER (Advanced Error Reporting) on the root port.** The kernel's AER service does not cover this hierarchy. Check the raw `CESta`/`UESta` fields in `lspci -vvv` after hardware or ASPM changes.
- **xpu-smi 2.1.0** segfaults in `discovery -d N` with compute-runtime 26.35 on this host; `config -d N` works. Read clocks and power from sysfs instead.
- **Engine resets.** The journal shows 51 GPU engine resets between 2026-08-16 and 2026-09-24; most of that span predates the upgrade. They match the symptoms of open [compute-runtime #948](https://github.com/intel/compute-runtime/issues/948); the cause is not confirmed.
- **Cold loads are disk-bound** once the uplink runs at Gen4: the Gen3 NVMe reads about 3.4 GB/s. Loading Qwen3.8-Flash-Next (111 GB) takes about 2.5 minutes.
